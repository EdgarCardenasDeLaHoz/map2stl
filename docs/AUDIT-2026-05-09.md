#### 🔧 Refactoring Opportunity: `app/server/core/export.py`

**Current Structure** (879 lines, mixed concerns):
```
1. ExportTask dataclass & task tracking (70 lines) ← could move
2. Export parameter parsing & caching (150 lines) ← could extract
3. DEM preparation & array manipulation (180 lines) ← can stay
4. STL/OBJ/3MF generation wrappers (100 lines) ← can stay
5. Label engraving & contours (120 lines) ← can stay
6. Puzzle export & tabs (140 lines) ← can stay
7. Cross-section generation (100 lines) ← can stay
```

**Recommended Split**:
```
app/server/core/export.py → core business logic (mesh generation, DEM prep)
app/server/core/export_tasks.py → ExportTask, task tracking, status endpoints
app/server/core/export_params.py → parameter parsing, cache integration
```

**Benefits**:
- Each module has a single responsibility
- Easier to test (task tracking can be unit-tested independently)
- Clearer mental model (task lifecycle separate from export logic)
- Maintain backward compatibility (export.py imports from both for public API)

**Decision**: This is optional — the current structure is functional and the file has good docstrings. Refactor only if you plan to add more task management features.
