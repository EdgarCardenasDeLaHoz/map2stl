## Part 2: CLAUDE.md Rules Evaluation

### Rule 1: `/compact` is user-triggered
**Status**: ✅ **Correct and necessary**

**Why sensible**: Context compression is fundamental to maintaining long sessions. Declaring it explicitly prevents the AI from accidentally running it and breaking conversation state.

**Clarity**: Good — explicit statement. But could note *when* the user should trigger it (post-commit, when responding to the compact signal).

---

### Rule 2: Load at most 1–2 docs files per session
**Status**: ⚠️ **Necessary but under-enforced**

**Why sensible**: 100+ docs files exist (see below). Loading them all would consume context immediately. Limiting to 1–2 keeps sessions focused.

**Problem**: No mechanism to enforce this. The rule is "good hygiene" but not structural.

**Improvement**: Could suggest which 1–2 docs to load based on task type (already exists in CLAUDE.md's "When to Read What" table — maybe just needs bold emphasis).

---

### Rule 3: Keep sessions focused on one module at a time
**Status**: ⚠️ **Aspirational but hard to enforce**

**Why sensible**: Scope creep is real. Skyline_cv work sprawled across 13 feature plans across multiple files.

**Problem**: No way to "lock" a session to a module. Relies on explicit user instruction.

**Suggestion**: Add a `/lock-module <name>` command (or similar) to make this enforceable. Or document that the user should state "focus on X module" upfront.

---

### Rule 4: Proposal + Plan + Edit workflow
**Status**: ✅ **Working well**

**Evidence**: F-SKY series exists entirely in `docs/plans/F-SKY*.md` with clear status tracking in `proposals.md`. Makes it possible to pick up work across sessions.

**Improvement**: The rule is clear, but `proposals.md` itself is now 8 KB and hard to scan. Consider:
- Splitting "active" (in-progress, approved) vs "completed" to the top
- Adding a date column to proposals so stale items are visible

---

### Rule 5: Edit hygiene (update docs same turn as code)
**Status**: ⚠️ **Stated but not verified**

**Evidence**: CLAUDE.md says to update docs, but no automated check. Recent skyline commit updated `city2stl/skyline/README.md` but didn't update `modules.md` or `issues.md` references.

**Improvement**: Add a checklist to commit responses:
- [ ] Updated module docstrings?
- [ ] Updated `docs/modules.md` function index?
- [ ] Updated `docs/issues.md` or `proposals.md`?
- [ ] Audited surrounding code for bloat?

---

### Rule 6: Seven Editing Rules (os.chdir, asyncio, modules, etc.)
**Status**: ✅ **Well-enforced and appropriate**

**Examples**:
- No `os.chdir()` found in codebase ✅
- `asyncio.get_running_loop()` used correctly in async functions ✅
- Frontend modules coordinate via `window.appState` ✅
- app.js exposes functions on `window.*` ✅

**Clarity**: Good. Could add a link in every file header pointing back to the rules, but existing code follows them well.

## Part 5: CLAUDE.md Sensibility Check

### Overall Assessment
**Rating**: ✅ **7.5/10 — Good foundation, needs operational clarity**

### What Works Well

1. **Context management** — `/compact` rule is the right lever
2. **Workflow** — Proposal + Plan + Edit is solid and evidence of it working
3. **Editing rules** — The 7 code rules are appropriate and well-followed
4. **Reading order** — The "When to Read What" table is genuinely helpful

### What's Missing or Unclear

1. **Commit signal** — Memory mentions "Run /compact before continuing" but CLAUDE.md doesn't explain where this signal appears (end of commit response?)

2. **Module lock** — Rule 3 (focus on one module) is hard to enforce. Consider adding:
   ```
   Sessions focused on task X should not edit module Y unless necessary.
   If you must edit multiple modules, explicitly ask the user before proceeding.
   ```

3. **Test requirements gate** — R-LAYER-LOAD mentions "Regression plan required before code movement" but there's no instruction on *how* to write one or where to store it.

4. **Priority guidance** — When multiple proposals are approved, which takes precedence? E.g., F-SKY5 (pending) vs P-PLANB-DEM (approved) vs B-STREAM (approved)?

5. **Documentation decay** — The rule says "update docs in same turn" but doesn't define "done." Is it enough to update a function docstring, or must `modules.md` also be synced?
